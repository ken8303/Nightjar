# Nightjar feature status

Reviewed 18 October 2026 against the original requested references and current source. Nightjar is a beta; this is a scope inventory, not a claim of production readiness or full feature parity. A single completion percentage would hide the difference between implemented features, missing features and device acceptance.

For exact test/build evidence and remaining release checks, use [BETA-HANDOFF.md](./BETA-HANDOFF.md) and [RELEASE-CHECKLIST.md](./RELEASE-CHECKLIST.md). Those records distinguish local work from the last successful GitHub validation and an actual Cloudflare deployment.

## Next work and acceptance criteria

1. **Close the existing release gates first.** On real iPhone/Android hardware, verify known-object camera alignment, a slow full turn, portrait/landscape, interruption and return, plus explicit stop/restart behavior. On an installed PWA, verify update with an unfinished edit, offline recovery and backup/recovery downloads. Run the final-origin checks after the user's next batch push. Record device/browser/build and actual results; leave unavailable checks pending.
2. **Validate and extend the new light-pollution map.** The 2025 Lorenz visual layer is implemented with explicit opt-in, legend, provenance, coverage and missing-tile recovery. [LIGHT-POLLUTION-DATA.md](./LIGHT-POLLUTION-DATA.md) records live response evidence and its narrower scope. Physical touch/installed-PWA and final-origin use remain pending. Any numeric sampler needs independent pixel/index, boundary, interpolation and nodata validation; do not infer a Bortle class from a colour or describe annual data as live.
3. **Validate atlas framing on devices and scope any wider-field extension separately.** The current Photo tools draft now supplies the 2D/3D atlas grid, with shared equipment validation, J2000 north/position angle, sampled edges and horizon clipping. Known 4° × 3° geometry, rotation, RA wrapping, grid ordering and mobile-sized browser flows are verified locally. Physical-phone rendering/performance still needs acceptance. Existing small-field limits remain explicit; this does not implement full-sky mosaics or mount control.
4. **Add satellites only with time-aware orbital data.** The proposed first slice and source/cache gates are in [SATELLITE-TRACKING.md](./SATELLITE-TRACKING.md); no tracking is implemented. Establish a permitted element source, propagation method, epoch/staleness policy and selected-time behavior. Verify known reference positions, below-horizon filtering, stale/unavailable feeds and foreground recovery. Do not imply visibility from geometric position alone.
5. **Treat photo recognition as a separate implementation.** Choose and validate an on-device solver/index strategy before adding a recognition claim. Require explicit image selection, clear progress/cancel/failure, bounded memory on phones, documented image handling and a verified sky-map handoff. Test successful, insufficient-star and incorrect-match cases.
6. **Scope further forecast/Moon expansions separately.** Seeing/transparency needs a provider and clear definitions; alerts need permission/delivery/lifecycle design; lunar shadow simulation needs its own model and validation. Existing nearby tools should not be relabelled to imply these capabilities.

This order is a development recommendation, not a promise that missing features have started or a replacement for the user's priorities. A concrete bug found in an existing flow takes precedence over adding another feature.
