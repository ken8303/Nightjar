# ISS directions and shared orbital cache

Implemented locally, 19 October 2026: Sky atlas has an optional ISS direction panel for the selected site and UTC instant. It shows geometric altitude, compass bearing and range, plus an explicit background search for horizon passes over the next 24 hours. Pass cards also estimate sunlight/shadow and Sun altitude at their highest point. Pass cards also intersect altitude, full-sunlight and twilight conditions into modelled observing windows. Brightness/weather screening, atlas/camera labels, live animation, other objects and notifications remain absent.

## Source evidence and numerical scope

The [CelesTrak GP format documentation](https://celestrak.org/NORAD/documentation/gp-data-formats.php) defines explicit CATNR/FORMAT queries, nine-digit identities and the omitted Earth/TEME/UTC/SGP4 metadata defaults. One normal HTTPS request to `gp.php?CATNR=25544&FORMAT=JSON` returned HTTP 200, application/json and one 422-byte ISS record on 19 October 2026. Its epoch was `2026-10-19T04:14:45.011040`. No further live GP request was made during development/QA; tests replay fixtures. The frozen record in tests is not shipped as a live-data fallback.

The installed, exactly pinned satellite.js 7.1.0 supplies JavaScript OMM ingestion, SGP4, TEME-to-fixed rotation and topocentric transforms. Its integrity matches the registry declaration previously recorded; the lockfile adds only that dependency and retains existing optional-platform metadata. The MIT notice is served and linked at `/licenses/satellite-js.txt`. The package root re-exports unused pthread/WASM runtimes which Vite tries to compile before tree shaking. A narrowly scoped build plugin removes only that pinned root's WASM re-export, checks its expected shape and preserves all JavaScript exports. It does not modify node_modules or vendor the propagation engine. The application does not use the package's WASM APIs.

Independent reference: the [Vallado/Crawford/Hujsak/Kelso AIAA 2006-6753 verification archive](https://celestrak.org/publications/AIAA/2006-6753/) supplies Vanguard 1's OMM-equivalent elements and TEME vectors at epoch and +360/+720 minutes. Those vectors pass a 0.02 km position and 0.00002 km/s velocity bound through this adapter. Independent Python WGS84 observer/IAU82 GMST transformations of the published epoch vector agree at ordinary, polar and date-line observers within 0.001° and 0.03 km. Vanguard is never relabelled as ISS. These are algorithm/frame checks, not empirical current-ISS positional accuracy or independently validated pass predictions.

Epoch parsing treats an omitted designator as UTC, validates calendar fields and preserves source fractional text while explicitly constructing a standard three-digit-millisecond UTC value for Date and SGP4 ingestion. It does not rely on browser-specific parsing of the source’s longer fractions. The application accepts only NORAD 25544; the generic parser retains up to nine digits for format validation. Unsupported frames/theories/versions, nonfinite/out-of-range elements and decayed/null propagation are unavailable. TEME vectors never enter the J2000 catalogue projector. The observer is explicitly at sea level, without refraction.

Current directions require a source epoch within three days of now, selected time within three days of that epoch, and source retrieval no older than six hours. A retrieval timestamp more than five minutes ahead of the device gets distinct clock guidance. These are conservative product limits, not accuracy guarantees. Freshness is rechecked each visible minute and on return from suspension. Geometric altitude is separate from naked-eye visibility. Pass cards estimate lighting only at their highest point; modelled windows combine altitude/shadow/twilight, while manoeuvres, weather, brightness and obstructions remain excluded.

## Shared acquisition and failure handling

The [provider policy](https://celestrak.org/usage-policy.php) requires minimal queries, one GP acquisition per two-hour update and stopping on non-200 HTTP responses for human investigation. `worker.ts` routes only GET `/api/satellite?object=25544` to the single named `SatelliteCoordinator` Durable Object. It ignores no arbitrary source/observer query: unsupported/duplicate parameters are rejected. All observers/regions of this Worker deployment use the same object name, rather than independent browser or per-isolate caches. Precise observer coordinates/time stay in the client.

`SatelliteFeedCache` coalesces concurrent reads and persists a halted pre-request fence before contacting CelesTrak. An interrupted request or failed post-response write cannot lose an unknown HTTP result and retry automatically. Successful replies preserve their actual completion timestamp; cached replies never re-stamp it. Requests have a 12-second source deadline and 16 KiB body bound; redirects are manual. Any non-200, invalid response or source-epoch failure remains halted for investigation. A failure before receiving an HTTP response permits a retry only after the persisted two-hour cooldown. Last good elements retain their original fetch time with explicit issue/paused metadata. Unreadable state or a failed fence write causes no source request.

End-user Retry cannot reset this policy state. There is no public reset endpoint. An operator must investigate the recorded HTTP/format/storage problem before reviewed maintenance clears a halt, retaining the attempted/deadline timestamps. Do not rotate object names, delete namespaces or reset migration tags as a retry mechanism. Separate preview/production deployments have separate namespaces; this is coordination within one deployment, not a global lock across every installation.

The client loads orbital data only after Load ISS directions. The propagation module is also conditional. Changing site/time recalculates locally without a source request. Closing, cancellation, timeout and retired results are handled separately from the shared server refresh; cancelling one browser request cannot cancel another observer's shared acquisition. No orbital reply enters the immutable PWA cache or local saved-plan format.

## Geometric pass search

After loading valid directions, **Find next 24 hours of ISS passes** launches a dedicated Web Worker, with no new orbital request and no site/time in a network URL. The search ends at the earlier of selected time + 24 hours or epoch + three days. A shortened window is explicitly labelled. An instant exactly at the upper epoch limit has no remaining search interval and receives guidance. Freshness/epoch failures remove the search and its results; changed site, instant or orbital snapshot retires the old calculator. Close/unmount, explicit cancellation, worker load/message failure and a 15-second deadline terminate the browser worker. Prior results for the same context survive cancellation/failure; changed context never retains them.

A reusable SGP4 record samples geometric elevation every 30 seconds. Local maxima are refined even when their surrounding samples are below the horizon, retaining grazing passes between samples. Golden-section peak refinement and bisection crossing refinement stop within 100 milliseconds of numerical interval width. That is solver resolution, not real-sky timing accuracy. The search is bounded to 12000 evaluations; a failed propagation makes the whole search unavailable rather than silently reporting an empty sky. Passes remain chronological, with UTC rise/highest/set and bearings. Already-up and still-up boundary states describe clipped events rather than inventing a rise/set. All observers remain at sea level without refraction.

Eight regression cases cover analytic rise/peak/set, a six-second grazing event between negative grid samples, no-pass, clipped boundaries, continuous-arc deduplication, failed propagation/calculation limits, epoch bounds, poles/date-line equivalence and reused-versus-fresh records. A separate exhaustive one-second search agrees with refined ISS timings within 1.1 seconds and peak elevation within 0.01° at London and Sydney test coordinates. Both searches share the previously reference-checked propagator: this checks the search method, not an independent SGP4 engine or measured current ISS accuracy.

The Vite worker import emits a separate calculator asset; both main/worker builds retain the pinned JavaScript-only library gate. Browser QA caught and corrected a build-time file URL produced by the framework with the initial import.meta.url form. The compiled CI check now rejects that file-URL failure, verifies the exact worker bytes are served as JavaScript and executes them through a Node worker message bridge against a frozen fixture. Native browser creation/cancellation still has separate rendered acceptance.

Local compiled-browser replay acceptance covers six chronological London passes without another feed request, cancellation/focus, worker load failure and retry, deadline guidance, changed-time retirement, unsupported dates, a shortened epoch-limited window and an already-underway pass. Portrait 320×568, landscape 800×360 and desktop 1100×800 fit without horizontal overflow. Browser plugin is unavailable; CUA IAB was used. Provider responses are local fixtures; no additional live GP request, push or deployment was made. Physical phones, independent observed pass comparisons and final-origin/PWA acceptance remain pending.

## Lighting at the highest point

Each computed pass carries an optional lighting sample at its highest point in the window: sunlit, partial shadow or Earth shadow, plus the geometric Sun-centre altitude at the sea-level site. A failed/unsupported sample leaves geometric pass times intact with explicit unavailable feedback. It does not turn missing lighting into a sunlit/visible classification or filter away geometric passes. Separate modelled-window calculations now cover conditions across each pass. Shadow/lighting has no separate source request or persisted user data.

The pinned library's [Sun and shadow documentation](https://shashwatak.github.io/satellite-js/docs/sun-and-shadow) pairs sunPos(jday).rsun in AU with propagate's ECI position in km. Its low-precision solar model is documented for 1950–2050; the adapter refuses lighting outside that interval. The Earth-shadow model uses a 6378.135 km sphere and apparent-disc overlap; atmospheric attenuation, detailed Earth shape and ISS brightness/orientation are excluded. Solar topocentric altitude uses the same ECI-to-fixed transform and sea-level observer with no refraction, separately from the J2000 catalogue projector. Nonfinite/inside-Earth/unit-inconsistent vectors or invalid shadow fractions return unavailable.

The [USNO twilight definitions](https://aa.usno.navy.mil/faq/RST_defs) use geometric Sun-centre depression of 6/12/18 degrees. The UI explains the civil limit without equating a dark site and sunlit satellite to guaranteed visibility. Modelled intervals below use these criteria with numerical refinement; they do not establish observed shadow timing or guaranteed visibility.

Four new regression cases cover sun-side/umbra/partial shadow against independent 192x384 apparent-disc area quadrature, invalid geometry/date/site limits, 80 Sun-altitude comparisons with Astronomy Engine and real-fixture pass lighting. Largest Sun-altitude difference is 0.005587 degrees across the selected dates/sites including poles and the longitude seam, below the 0.02-degree test bound. The quadrature checks the documented approximate disc model, not an independent atmospheric/real-sky eclipse simulation. The compiled pass-worker check also asserts shadowed and sunlit-twilight fixtures.

CUA local replay confirms the first two London peaks are shadowed at Sun altitude -39.5/-26.6 degrees, the third is sunlit at -11.9 degrees, and later sunlit peaks include daylight. Partial shadow and unavailable lighting use explicit synthetic worker fixtures; unavailable lighting preserves horizon times. Selected-time changes recompute locally, with no additional GP request. Desktop/320 portrait/800 landscape containment and console health pass. Physical phones, installed-PWA and observed-sky accuracy remain pending.

## Modelled observing windows

Each geometric pass retains its horizon times, peak facts and exact-time shortcut. Optional observing windows intersect three strict model conditions: altitude above 30 degrees, the entire solar disc clear of the spherical Earth-shadow disc, and geometric Sun-centre altitude below -6 degrees. Only overlaps at least ten seconds long are shown. These are explicit product criteria, not an exhaustive visibility claim: partial-shadow/low-altitude or shorter opportunities can be excluded, and brightness, weather, Moon glare and terrain are not screened. The UI shows the criteria and keeps all geometric passes, including daytime/no-match passes.

Sun clearance is the angular centre separation minus the apparent Earth/Sun disc radii, using the same geometry/constants as the documented shadowFraction model. Its sign agrees with the full-sunlit boundary in the checked samples. Each smooth condition is searched separately with the existing 30-second/extremum refinement, then the refined intervals are intersected. This retains a short common overlap missed by sampling the combined boolean predicate. Root intervals stop at 100 ms numerical width; that is solver resolution, not real-sky timing accuracy. Ten-second minimum duration avoids presenting subsecond numerical overlaps as useful windows. Per-search memoized condition samples have a shared 6000-evaluation ceiling; any failed model/calculation is unavailable, distinct from a successful no-match result. A pass below the altitude criterion can establish no match without requiring a lighting sample. All calculations stay in the same cancellable, deadline-bound browser worker.

Windows clipped by the selected/epoch search boundary are labelled. Changing site/time/data retires them with the parent pass search. Missing windows preserve available geometric times/peak facts/shortcuts. No provider, cache policy, persistence schema or dependency was added.

Nine new regression cases cover live-result summaries, analytic intersections, an eleven-second overlap between negative combined-grid samples, an explicitly excluded nine-second overlap, disjoint/non-mutating interval intersection, failed inputs/propagation/evaluation limits, solar-clearance consistency, selected-boundary clipping and unsupported solar-model dates. A separate one-second combined-condition scan agrees within 1.1 seconds across London, Sydney and 45 N/135 E test coordinates. That third case begins on shadow exit while already at 34.4 degrees altitude: one second before the refined start is partially shadowed, one second after is fully sunlit. This independently checks search topology using the previously checked propagator/shadow model, not a separate SGP4 engine or observed satellite visibility.

Compiled-browser replay confirms the London 2026-10-20T05:19:24Z–05:22:20Z window, excludes the higher daytime pass, and retains eight Sydney geometric passes with no matching windows. An explicit synthetic unavailable-window result differs from no match while retaining times. The exact peak shortcut yields a correctly labelled clipped start with no additional feed request. Compact 320x568, landscape 800x360 and desktop 1100x800 fit; nested window items do not inherit outer pass-card borders/padding. The polite result summary counts matching windows and separately announces unavailable calculations. Warnings/errors and framework overlays are absent. Physical phones, installed-PWA and final-origin/observed-sky acceptance remain pending.

## Calendar snapshots — 20 October 2026

Each qualifying window offers Download calendar, producing one tentative UTC event. Whole-second start/end values round inward, while the notes retain original millisecond bounds, the model criteria, observing name/coordinates/time zone, orbital epoch, successful retrieval timestamp and any paused-source warning. Clipped search boundaries remain explicit. The file is a fixed snapshot; it does not refresh and says to recheck Nightjar before observing. The UI states that site name and coordinates are included and calendar apps display times in their own time zone.

Download revalidates feed identity, retrieval age, device clock and epoch bounds at the user gesture. A stale clock/feed error leaves the current selected time and cards unchanged. A still-valid last-good feed can be exported with its paused-refresh/source issue preserved. The action does not apply a new observing time or request new source data. The serializer shares the existing calendar text escaping, UTC formatting and UTF-8 folding in lib/calendar-format.ts; the existing forecast/eclipse/deep-sky/meteor calendar suites remain passing. Calendar-format reference: [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545.html), sections 3.1, 3.3.5, 3.3.11 and 3.8.2.2.
